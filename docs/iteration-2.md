## 3. 性能优化前后对比

本迭代没有引入构建工具或第三方运行时依赖，页面资源只有 HTML/CSS/JS/JSON。测量口径：Node v26.13.0 下直接 `require` 纯函数模块，重复运行取平均；资源体积为 `src/` + `data/` 的字节数。

| 指标 | 优化前 | 优化后 | 做了什么 |
| --- | --- | --- | --- |
| Lighthouse Performance | 未测 | 未测 | 沙箱禁止启动 headless Edge（mojo Access denied），待第 15 周在本地 Chrome 跑 |
| 首次内容绘制 FCP | 未测 | 未测 | 同上；页面零运行时依赖、无网络字体，静态资源合计 144.4 KB |
| 60 节点双画布帧率 | — | 未测（纯计算：整场 60 步 1.19 ms） | 每步用 `stepState(i)` 从插入顺序重建两棵树，无累积状态；单步 0.02 ms，折线序列 60 步共 9.63 ms，预期远低于 16.7 ms 一帧 |
| 页面资源体积 | 第 9 周骨架：约 44.6 KB（src 38.7 + data 5.9） | 144.4 KB（src 129.3 KB + data 15.2 KB） | 增加三页完整交互、共用树模块、折线图与全部 JSON 文案；仍无第三方运行时库 |

补充测量（同一口径）：

| 项 | 耗时 |
| --- | --- |
| d3 单步（重建双树 + 三项读数） | 0.02 ms |
| d3 整场 60 步 | 1.19 ms |
| d3 全部 60 步折线序列 | 9.63 ms |
| d2 四种删除计划（8 步 × 4 种情形/策略） | 0.25 ms |
| d1 单次路径 + 候选计数（7 节点） | 0.01 ms |

结论：纯逻辑开销可以忽略，真正影响首屏的是资源体积与渲染次数；因此没有做「提前优化」，只保证了确定性重算与单一数据流。

## 5. 问题与改进

- 遗留 bug 清单（按优先级）：
  1. P1：真实浏览器视觉未验收（双画布 + 折线在 1440/1024/680 三种宽度下的排版）——沙箱无法截图。
  2. P2：Lighthouse 未跑，性能对比表缺 Lighthouse/FCP 两行。
  3. P2：d3 的折线纵轴固定为树高，平均/最坏步数只能改 JSON 的 `chart.metric` 切换，没有 UI 切换。
  4. P3：n≥23 时 compact 模式隐藏节点数字（为避免 60 节点挤在一起），属于刻意取舍。
- 原因：沙箱环境没有可用浏览器；折线 UI 切换属于第 15—16 周的打磨项；节点数字的物理空间限制。
- 第 15—16 周怎么收尾：①在本地 Chrome 跑 Lighthouse（Performance / Accessibility / Best Practices），把分数与 FCP 截图补到本报告；②在三种宽度下截图检查排版；③给折线加「树高 / 平均步数 / 最坏步数」切换（复用 `chartSeries` 的 metricKey）；④部署 Gitee Pages 后用线上地址复测。
